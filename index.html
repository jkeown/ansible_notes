Ad hoc Commands

Common commands

ansible HOSTS -m pingTest connectivity to managed nodes

ansible HOSTS -a "REMOTE_COMMAND"Execute cli commands

ansible HOSTS -m shell -a "REMOTE_COMMAND"Execute cli commands when above doesn't work. Sometimes the terminal shell is necessary for the command to run

ansible HOSTS -m setup -a "filter=ansible_fact" -bDisplay specific ansible_facts info

ansible HOSTS -m setup -b > facts.txtSaves all facts to text file which can be searched using vi or also "grep -A50 FACT_NAME" which displays the fact and the following 50 lines also (-A50 can be adjusted of course)

ansible localhost -m setupGather control node info only

ansible localhost -m debug -a "var=groups"Displays the contents of the magic variable "groups". Useful for generating /etc/hosts 🛈

ansible localhost -m debug -a "var=hostvars['host_name']"Display only the variables assigned to the current target node. See hostvars for more info

ansible host -m debug -a "var=vars"Display only the variables assigned to the specific target node. Similar to above but simpler

ansible group -m debug -a "var=vars"Display the variables assigned to an entire group of nodes

Playbook Commands

Commands / Options

Options are run with ansible-playbook ... unless otherwise noted

--syntax-checkVerifies code syntax only. Does not connect to hosts or check runtime variables

--check or -CSimulates actual execution. Connects to hosts and checks runtime host/group variables

--start-at-task="task_name"Executes playbook code starting at the specified task. Argument must match task name exactly

--tags="tag_name"Runs only the tasks labeled with the specified tag name

-e "variables"Pass in arguments that override playbook variables.
EXAMPLE: -e "http_port=8080"

--ask-vault-passPrompt for vault password when running playbook with encrypted data

--vault-password-file path_to_fileSpecify the vault password file to use when running playbook with encrypted data

Custom / Dynamic Variables

Dynamic variables can be set using the ansible.builtin.set_fact module. The variable value will depend on the condition


  ansible.builtin.set_fact:
  # idiomatic Jinja2 pattern, heavily used in Ansible. (Python ternary)
    web_port: "{{ '8081' if inventory_hostname in groups['web'] else '2049' }}"

Custom Facts are created under /etc/ansible/facts.d on the managed nodes. They can be static files or scripts. Both file types must have the .fact extension. JSON format is ideal because it supports nested structures, lists, and booleans cleanly. The file /etc/ansible/facts.d/my_custom_fact.fact would be referenced like so:


  ansible_facts['ansible_local']['my_custom_fact']['custom_key']

  # Reference Structure Breakdown
  {
  "ansible_facts": {                      # 1. Root
    "ansible_local": {                    # 2. Category - namespace Ansible uses to hold custom local facts gathered from the remote target machine
      "custom_fact": {                    # 3. File Name
        "custom_key": "your_value_here"   # 4. Specific Data Point
        }
      }
    }
  }

Custom fact file content example:


  # INI format
  [settings] # arbitrary section header - not needed in JSON format
  environment=production
  billing_code=finance-101
  is_clustered=true

If you use the INI format, Ansible treats every value as a raw string. In the INI example, is_clustered=true will be read as the string "true", not a true boolean. If you try to use a conditional like when: ansible_facts['ansible_local']['server_meta']['settings']['is_clustered'], it will not evaluate correctly. For this reason, JSON is heavily preferred.

Instead of writing an independent file on the target server, you can use Ansible's built-in set_fact task module (above). This evaluates values dynamically directly inside your runtime playbook memory without dropping files on the managed host

Variable Files

Variables are most often stored under host_vars and group_vars directories. The variable file is named after the group the variables target.
Example: The hosts in the inventory file of the group [webservers] will use the variables in group_vars/webservers.yml

Variable Snippets

Often used variables/facts to commit to memory

inventory_hostnameExact name of the host as defined in the inventory file. Changes dynamically for each host the playbook runs against. This variable is available even without gather_facts. Best to use when comparing against "groups" or "hostvars"rather than ansible_facts['hostname']

groups['group_name']List of inventory names strictly pulled from the inventory file. It does not know what the actual operating system calls itself.


  # Runs task only when host is part of specified group
  when: inventory_hostname in groups['GROUP_NAME']

Ansible Facts contain data pertaining to the system, hardware, network, users, storage, filesystems, environment variables, python environment, date, time, virtualization, and custom local facts. Real-time OS state

Following are often used Ansible Facts:
(This syntax is legacy and relies on "fact injecting" which can be disabled)
ansible_os_family
ansible_distribution
ansible_default_ipv4.address
ansible_hostname

The modern way to use the same facts:
ansible_facts['os_family']
ansible_facts['distribution']
ansible_facts['default_ipv4']['address']
ansible_facts['hostname']

Hostvars:
An internal, read-only dictionary stored in the memory of your control node. It contains all variables for all hosts defined anywhere in your project (from host_vars/ files, group_vars/ files, your inventory file, and previously gathered facts if they exist) which are organized by hostname. Because hostvars maps everything together, it allows one host to "peek" into the properties of another host during a playbook run


  # How to reference
  {{ hostvars['web01']['ansible_facts']['env'] }}
